# 故障排查

本页按用户看到的现象排查 Snap Workspace 0.9.6。先在工作区卡片选择“检查”，再尝试恢复；状态栏的工具提示包含逐应用准备结果。

> 不要通过反复强制结束应用来掩盖身份或启动问题。先区分是 Shell 能力、窗口匹配、后台保证、原生提交还是兼容定位阶段失败。

## Route 3 显示不可用

可能原因：

- `windowsudk.shellcommon.dll` 不存在；
- 运行类无法激活；
- `IsSupported` 返回否；
- `ISnapLayoutManager2/3` 查询失败；
- 不是 Windows 11 x64 或系统组件状态异常。

处理：

1. 打开设置，记录 Route 3 状态；
2. 运行只读探测：

   ```powershell
   dotnet run --project SnapWorkspace.Route3.Demo -c Release -- probe
   ```

3. 导出默认隐私级别的支持包；
4. 报告 Windows build、Shell DLL 版本与 SHA-256；
5. 不要把其他电脑的系统 DLL 复制进应用目录。

未知 Shell 哈希本身不会阻止原生路径：如果运行类、`IsSupported`、manager 和 v2/v3 接口全部通过，能力卡片会显示“运行时兼容”。只有实际能力探测失败时，包含原生窗口的工作区才会被预检阻止；兼容和后台角色仍按各自路径运行。

## `SnapWindows` 返回成功，但窗口没有正确吸附

后端会在调用后读取 DWM 可见边界。若任何窗口与目标边界相差超过容差，结果会标记为失败，而不是补一次普通位置调整。

检查：

1. 确认应用没有在启动后自行最大化、恢复旧位置或显示模态框；
2. 确认窗口样式支持 Snap；
3. 把验证延迟留在 250–1500 毫秒范围，慢启动应用可适当增加；
4. 只保留一个明确窗口候选，或收紧匹配规则；
5. 用“重新恢复”再次提交完整布局。

如果应用本身拒绝 Snap，应改为“兼容定位”，不要把几何到位等同于 Snap Group。

## 可视化编辑后不再受 Snap 控制

原因通常是编辑结果变成任意矩形或删除 Zone 后的缺口布局。原生路径只接受完整内置模型。

处理：

1. 打开“可视化编辑”；
2. 选择“应用原生模型”或“恢复初始布局”；
3. 需要桌面空白时清空槽位中的应用，不要删除 Zone；
4. 如果必须使用任意位置，把相关应用改为兼容定位。

预检错误 `native-layout-unsupported` 正是在阻止“看似正确但不属于 Snap Group”的状态。

## 原生窗口超过 4 个

当前 Route 3 基线一次最多提交 4 个原生窗口。智能捕捉只限制原生集合，不限制整个工作区。

处理方式：

- 只保留最多 4 个原生窗口；
- 把额外可见应用改成兼容定位；
- 把无须显示的应用改为后台；
- 把无关应用设为忽略或加入屏蔽规则。

## 工作区只恢复了一部分窗口

这是明确的部分恢复行为：某个可见应用缺失时，只要其他可见窗口已准备好，剩余窗口继续恢复，缺失 Zone 显示桌面。

在状态栏工具提示中找到该应用：

- `NotLaunchable`：没有 EXE、AUMID 或 URI；
- `Failed` 且提示路径不存在：安装路径已变化；
- 已发启动请求但 15 秒内无匹配窗口：启动器、标题或窗口类不符合规则；
- 有多个同分候选：需要更明确的标题或类规则。

编辑工作区，更新启动目标和匹配规则，再恢复。

## 进程存在，但应用没有任务栏窗口

进程存在不代表桌面窗口已准备。浏览器、Electron、启动器和驻留程序经常有后台进程但没有可见顶层窗口。

Snap Workspace 对窗口角色最终要求匹配 HWND：

- 不要把任务管理器中的进程数量当作恢复成功；
- 窗口应用应有可启动目标和可识别窗口；
- 后台应用只要求无可见窗口，并不创建一个可供 Snap 的前台窗口；
- 单实例程序若已被后台模式启动，前台启动方式必须由应用自身支持。

Chrome 在 0.9.5 使用 `--no-startup-window`，不会通过先创建再隐藏主窗口来污染前台会话。

## Chrome 作为后台后无法正常打开

先确认运行的是 0.9.5 或更高版本。旧版本曾使用通用隐藏策略，可能让单实例浏览器保留被隐藏的主窗口。

0.9.5 的预期行为：

- 后台恢复给 Chrome 添加 `--no-startup-window`；
- 不隐藏已有用户窗口；
- 后续普通启动可以快速出现前台窗口；
- 如果没有后台组件，Chrome 进程可能自行退出。

若仍无法打开：

1. 结束由旧版本遗留的全部 Chrome 进程一次；
2. 确认工作区参数中没有用户手工加入会阻止窗口的开关；
3. 恢复后台工作区；
4. 立即从开始菜单普通打开 Chrome；
5. 导出含应用明细的支持包前先检查隐私内容。

## 后台应用仍然显示窗口

后台阶段会在启动前注册守卫、监听窗口创建/显示、扫描兜底并跟踪子进程。600 毫秒检查时仍有可见窗口就会把后台项标记失败，并跳过桌面阶段。

常见原因：

- 目标以更高权限运行，普通权限 Snap Workspace 无法控制；
- 启动器创建了无法关联的独立进程；
- AUMID 无法解析为实际 EXE；
- 应用持续自行显示窗口；
- 应用需要专用后台参数。

处理：

1. 在工作区中确认实际 EXE/AUMID；
2. 不要仅用宿主进程名，例如 `ApplicationFrameHost.exe`；
3. 检查应用官方是否有驻留、静默或无窗口参数；
4. 对普通桌面程序，可尝试与目标相同权限运行 Snap Workspace，但要了解提权风险；
5. 如果该应用本来就需要显示在桌面，把它改成兼容定位，而不是后台。

后台守卫只在恢复事务内有效。事务结束后点击托盘图标应立即显示；如果仍被延迟隐藏，记录准确时间并提交支持包。

## Everything 后台启动仍弹窗

Everything 使用专用顺序：`-close` → 等待约 250 毫秒 → `-startup`，同时使用通用守卫。

检查：

- 工作区 EXE 是否指向真正的 `Everything.exe`；
- 是否有另一个不同权限的 Everything 实例；
- Everything 版本是否支持这些参数；
- 启动参数中是否有冲突开关。

## 兼容窗口变成左上角小标题栏或 1×1

0.9.5 已修复旧的逐边裁剪问题。新捕捉会优先使用 `WINDOWPLACEMENT` 的正常还原矩形；异常小窗口会被阻止保存。

对于旧工作区：

1. 先把目标应用恢复到正常大小；
2. 执行一次工作区恢复；
3. 若读取到有效当前矩形，软件会修复并保存；
4. 若仍失败，在捕捉页用“手动点选窗口”重新捕捉；
5. 确保点击的是主窗口，不是悬浮工具条或隐藏宿主。

修复保存前会在 `backups\<workspace-id>` 留下旧定义。

## 兼容窗口被原生窗口覆盖

恢复顺序是原生 Snap 后再定位兼容窗口。冷启动且矩形相交时，兼容窗口会获得短暂前景租约，等待原生应用晚激活后再取消置顶。

若仍被覆盖：

1. 确认两者确实有交叠；
2. 确认兼容窗口没有在恢复结束后自行重建 HWND；
3. 检查是否有多个同名窗口导致匹配了错误实例；
4. 收紧路径、标题和窗口类规则；
5. 尽量减少兼容区域与原生 Zone 的大面积重叠。

Snap Workspace 不维持永久置顶，也不持续纠正 Z-order；恢复完成后的应用主动激活属于正常桌面行为。

## 应用未被智能捕捉识别

常见情况：窗口标题为空、工具窗口样式、没有任务栏入口、托盘注册无法解析、被屏蔽或启动身份重复。

按顺序尝试：

1. 开启相应捕捉范围；
2. 查看设置中的捕捉屏蔽列表；
3. 选择“重新自动分类”；
4. 使用“手动点选窗口”；
5. 在编辑器中从已安装应用添加；
6. 对特殊程序手工填写 EXE/AUMID 和匹配规则。

手动点选允许无标题顶层窗口，但仍会过滤 Snap Workspace 自身及无效区域。

## 捕捉出大量系统进程

默认只开启任务栏范围。托盘和纯后台范围可能包含大量驻留软件。

建议：

- 只在需要时临时开启托盘或纯后台；
- 使用“屏蔽”移除 Defender、驱动控制面板等不属于工作区的项目；
- 在设置中添加路径、发布者、包族或名称通配规则；
- 使用“全部忽略”后只选择必要项；
- 只对稳定、确实需要复用的角色点“记住”。

## 窗口匹配错了实例

症状包括浏览器选错页面、编辑器选错项目或多窗口程序互换槽位。

建议从宽到严调整：

1. 完整路径 / AUMID；
2. 要求窗口类相同；
3. 标题包含稳定项目名；
4. 通配符；
5. 必要时使用有边界的正则。

避免用完整动态标题，例如包含当前文档名和未保存标记的整串文字。也不要同时忽略进程、标题和类名。

## Windows 设置没有启动

`ApplicationFrameHost.exe` 是窗口宿主，不是可直接启动的设置应用。当前 schema 读取时会识别“设置/Settings”窗口并把启动目标迁移为 `ms-settings:`。

如果旧工作区仍失败：

1. 编辑该应用，检查启动目标；
2. 删除后重新捕捉 Windows 设置；
3. 运行工作区“检查”，确认没有把宿主 EXE 当成唯一启动路径。

## Obsidian 或其他应用无法 Snap

如果你已手工确认该应用无法进入 Windows Snap Layout，就直接使用兼容定位。运行时结构检查也会把明显不支持 Snap 的窗口从原生批次路由到对应 Zone 的兼容分配。

兼容位置接近原生 Zone 不会使它成为 Snap Group 成员，这属于设计边界。

## 快捷键无效

检查：

- 设置页总开关是否开启；
- 该动作自身是否启用；
- 快捷工作区槽位是否已分配；
- 组合是否至少含一个修饰键；
- 是否与另一个动作重复；
- 是否被系统或其他软件占用。

应用使用 `RegisterHotKey`，系统拒绝的组合会在设置页显示原因。更换组合后会立即重新注册。

## 关闭窗口后应用仍在运行

若启用了“关闭时进入托盘”，关闭按钮只隐藏主窗口。要彻底退出，请使用通知区域菜单中的退出命令。

“结束工作区”也不是结束所有进程：它默认只取消会话管理；用户确认后，也只向本次恢复新启动的可见窗口发送普通关闭请求，后台和既有窗口保留。

## 常驻内存比预期高

完整主窗口使用 .NET 10 WPF、Fluent 资源、布局预览、应用清单和运行时 JIT/程序集缓存。Windows 任务管理器的工作集还包含可回收页面，不等同于持续活跃内存。

降低不使用时占用的方式：

- 启用登录启动并选择直接进入托盘，使启动阶段只创建轻量消息宿主；
- 避免长期停留在包含大量应用清单的捕捉页；
- 完全退出可释放整个运行时；
- 评估时同时观察私有工作集、提交大小、空闲后变化和 CPU，而不是只看一个总工作集数字。

当前项目优先保证现代 UI、DPI 和实用性，不以牺牲界面为代价追求极端小内存。

## 导出支持包

1. 打开“设置 → 诊断与隐私”；
2. 先保持两个敏感选项关闭；
3. 选择“导出支持包”；
4. 自行检查 ZIP；
5. 只有定位路径/标题问题时才启用应用明细；
6. 只有需要复现完整定义时才启用工作区 JSON。

默认包包含系统/运行时、Route 3 能力、匿名数量、设置摘要和最多 7 天事件。软件不会自动上传。完整字段见 [隐私与诊断](PRIVACY_AND_DIAGNOSTICS.md)。

## 安全重置

仅清除诊断：在设置中选择“清除诊断事件”。

恢复某个工作区旧版本：

1. 彻底退出 Snap Workspace；
2. 备份整个 `%LOCALAPPDATA%\SnapWorkspace`；
3. 从 `backups\<id>` 选择旧 JSON；
4. 复制为新的临时 `.json`，通过 UI 导入；
5. 不要直接覆盖现有文件，先验证导入副本。

这种方式保留当前定义，失败时可回退。
